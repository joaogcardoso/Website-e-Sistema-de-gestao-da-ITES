# Integração contínua e bloqueio de pull requests

O workflow `.github/workflows/ci.yml` executa em pull requests para `main`, em atualizações de `main` e manualmente. A etapa `CI / web` instala dependências e executa verificação TypeScript, lint sem avisos, testes e build. `CI / server` executa `./mvnw verify`, incluindo testes PostgreSQL via Testcontainers. `CI / deployment` valida o Compose, constrói as imagens, inicia os três serviços, aguarda os health checks, verifica portal em pt-BR, sete páginas públicas e 401 em rota protegida, e confirma a retenção de um registro após recriar os contêineres. O job agregado `CI / ci-success` falha se qualquer etapa estiver com falha, cancelada ou ignorada.

Para bloquear efetivamente merge no GitHub, uma pessoa administradora do repositório precisa ativar proteção da branch ou ruleset para `main` e tornar `CI / ci-success` uma verificação obrigatória. Ative exigência de pull request, branch atualizada antes do merge e bloqueio de merges quando a verificação estiver pendente ou falhar. A configuração remota não pode ser criada pelo workflow e ainda precisa ser conferida na página de configurações do repositório.

O job `CI / deploy-production` roda somente após `CI / ci-success`, em push aprovado para `main`, e referencia o ambiente `production`. A proteção desse ambiente não é automática: configure no GitHub restrição à branch `main` e revisores obrigatórios conforme a política de implantação. Antes de chamar Dokploy, confirma que o SHA validado ainda é o atual da branch principal. Configure nesse ambiente as variáveis `DOKPLOY_URL`, `DOKPLOY_COMPOSE_ID` e o segredo `DOKPLOY_API_KEY`. Sem essas configurações o deploy falha de forma explícita; pull requests nunca recebem esses segredos.

O job de deploy dispara o build no Dokploy de forma assíncrona; o resultado do build e health check posterior precisa ser conferido na plataforma. A API do Dokploy não fixa o checkout em SHA, portanto uma atualização concorrente após a checagem ainda pode causar divergência entre o SHA validado e a revisão implantada. Para operação estrita por SHA, publique imagens imutáveis e implante pelo digest.

A CI não configura regras do GitHub. Uma pessoa administradora ainda precisa exigir `CI / ci-success`, pull request e branch atualizada nas regras de `main`.
